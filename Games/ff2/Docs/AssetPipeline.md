# Native art export: Batch 01

The approved concept direction is the reference for new ImageGen source sheets. Batch 01 contains 32 environment tiles at **16 × 16** pixels and 12 directional Firion walk frames at **16 × 24** pixels. This production proof starts the asset library; it does not cover the campaign or reproduce audited original maps.

## Reproduce

From the repository root, with Node.js and `sharp` available:

```powershell
node Tools/art-pipeline/export.cjs
node Tools/art-pipeline/verify.cjs
```

The exporter first tries the ordinary `sharp` package, then the bundled runtime at `C:/Users/const/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/sharp`. No network/API request is made by either script. Source generation happens separately with ImageGen. While a character source is still pending, export the two tile sheets only with `node Tools/art-pipeline/export.cjs Tools/art-pipeline/batch01.json --tiles`; the manifest is then explicitly marked `partial: true`.

`Tools/art-pipeline/batch01.json` is the repeatable slot contract. Sources are `ArtSource/Batch01/terrain.png`, `town-dungeon.png` and `firion-walk.png`. Terrain and structures use 4 columns × 4 rows. Firion uses 3 columns × 4 rows: down, left, right, up. Columns are left foot, idle, right foot; playback is 0, 1, 2, 1 at 160 milliseconds per displayed frame.

Grid boundaries use integer partitioning of the actual source dimensions. This handles sheets whose dimensions are not evenly divisible by four. Optional `region` and `cellRects` settings allow a visually confirmed crop to be recorded without changing source images. Every exported entry records the exact source rectangle, source dimensions and SHA-256.

## Permitted mechanical operations

- Crop generated slots and resize tile slots to 16 × 16 with nearest-neighbor sampling.
- Convert sprite alpha below 128 to transparent and alpha at or above 128 to opaque.
- Measure each sprite's visible bounding box. Use **one shared scale** across the entire 12-frame sheet, with a 16-pixel maximum visible width and 24-pixel maximum visible height. Center each visible body horizontally and align its lowest visible pixel to the bottom of the 16 × 24 frame. The source's broad scarf silhouette means the body does not fill the entire canvas height.
- Assemble review atlases, labeled contact sheets and sample maps from exported assets. These are review evidence outside Unity's production-import directory.

No tile pixels are painted, blended, mirrored, edge-corrected or procedurally generated by these scripts. No palette quantization is applied. The small output resolution necessarily discards source detail; source sheets remain intact for later revision. Sprite bounding-box normalization may introduce a one-pixel change from rounding; animation needs visual inspection and later Unity playtesting.

## Outputs and Unity contract

Individual numbered PNGs live in `Assets/Art/Production/Batch01/{terrain,structures,firion}/`. Native atlases live only under `Review/production/`, preventing duplicate Unity sprite imports. `Assets/Art/Production/Batch01/manifest.json` declares stable IDs (`batch01:terrain.path-nw`), repository-relative file paths, group, kind, dimensions, 16 pixels per unit, point filtering, pivots, animation direction/frame, output hashes and source provenance. IDs use a single namespace separator, consistent with `Core.ContentId`. Tile pivots are `(0.5, 0.5)`; field actor pivots are bottom center `(0.5, 0)`.

Generated files can be regenerated. The exporter refuses to replace an existing PNG if it differs both from the new export and from the previous manifest's output hash. It never deletes stale, extra or unrelated files. A renamed or retired asset therefore requires an explicit maintenance decision rather than automatic cleanup. New assets/folders receive deterministic GUID `.meta` files. Existing metadata is always preserved; Unity's production importer applies the native sprite settings during import. Actual Unity import is a separate validation step.

## Review evidence and limitations

- `Review/production/contact-sheet.png`: all assets enlarged by an integer factor, with IDs readable from group/name.
- `terrain-contact.png`, `structures-contact.png`, `firion-contact.png`: group atlases at 8×.
- `firion-detail.png`: comparison at 32 × 48 pixels per frame, freshly sampled from the same source at twice the shared scale and enlarged 4×. It is review-only, outside Production; it does not change native field footprint or import contract. Fine source shading is more legible here than in the native 16 × 24 proof.
- `path-assembly.png`: the nine path transition tiles assembled with an outer grass border.
- `repeat-materials.png`: repeated grass, water, cobble, dungeon floor and earth samples.
- `hut-assembly.png` and `town-dungeon-sample.png`: roof/wall/door assembly and adjacent town/dungeon asset samples. These are illustrative layouts, not reconstructed original maps or a playable map.
- `animation.html`: local browser animation preview with pause/play. This does not prove Unity runtime behavior.
- `validation.json`: native dimension/ID/hash/alpha checks and exact edge diagnostics.

The exporter compares all 12 interior horizontal/vertical edges of the 3 × 3 path patch, and compares opposite edges of every individual tile. It reports exact mismatched-pixel counts and channel differences. Identical edge pixels are a conservative diagnostic, not a requirement for naturally textured neighbors or proof of seamless art. **This batch does not claim seamless tile coverage.** Inspect the assembled path and repeated materials for visible seams. More terrain transitions, shoreline coverage and production maps remain separate work.

`verify.cjs` independently reads the delivered files and validates output/source/config hashes, crop bounds, unique IDs and paths, native dimensions, import declarations, binary alpha, directional frame counts and review artifact presence. This is file evidence; Unity Editor import, runtime animation and playable-build validation must be recorded separately by the Unity integration workflow.

The generated walking sheet has similar left/right stride poses. Hand cleanup or another generated revision remains desirable for stronger walk readability; file checks cannot establish animation quality. Source crops preserve complete poses despite uneven vertical spacing in the generated sheet. Terrain/structure source revisions are made with ImageGen and retained separately; the latest exported source hashes identify exactly which revision was used.

This is a first asset batch with explicit cleanup needs, not a complete seamless map kit. Unity import/play/build evidence belongs to the Unity integration report.
